# Devlog

## 2026-10-31 — First Linux boot

Started the Linux port from the Windows recompilation by David Petersson. The upstream tools for reading the disc already work anywhere Python runs, so I imported them directly instead of going through the Windows-only setup script. My retail ISO passed both hash checks (the executable and the menu archive), and the menu patch that removes Xbox Live and shortens the startup applied cleanly.

ReXGlue has no prebuilt Linux SDK that matches upstream, so I built tag v0.10.0 from source with its Linux release preset and installed it inside the project. Pinning that exact tag matters: upstream's native edits are checked by hash against the generated code, and all 17 of them matched on the first try. Code generation takes about five seconds.

The Windows-specific code in the game layer turned out to be small. The Windows header, the Direct3D 12 tearing option and the Windows font lookup are now only compiled on Windows; on Linux the loading font comes from the usual system font folders, and the executable folder comes from the SDK instead of a Win32 call. Turning vsync off is enough for high-framerate presentation on Vulkan, which chooses mailbox or immediate mode by itself. The CMake project now copies the runtime library and the Vulkan GPU plugin next to the game, because the SDK loads the plugin from the executable's own folder.

In place of the Windows launcher there is a small shell launcher that reads `tt-recomp.ini` and accepts the same options as flags, then starts the game with the same engine settings the Windows launcher uses. `build.sh` runs the whole chain from ISO to a runnable `dist/` folder. FSR and CAS are not available yet because the SDK was built without FidelityFX, so the launcher defaults to bilinear scaling.

The first build compiled and linked without errors in about 36 seconds with clang 23 and ninja. On the first run, in a virtual display on an RTX 3070, the game mounted the ISO, picked up the offline menu archive, started audio, and played the copyright screen followed by the Rockstar logo intro. That is milestone 4.

Still open: the presentation counter reported about 15 FPS for the whole run, which may come from the virtual display rather than the game, and needs a run on a real display to tell. Next comes reaching the main menu and a match, then audio, controller and save checks.

## 2026-10-31 — Into a match, and a faster way to test

The game now gets all the way into a match on Linux. From the main menu it goes through the Tournament screens, the venue fly-over and the player introductions, and then plays points: serves, rallies, the rally counter and the score all work. The match music and sound effects come out of the speakers, and the game writes its save file and thumbnail to the user data folder.

Most of the session went into making test runs faster. Every check meant launching the game in a virtual display, sitting through the intro and clicking through menus, and the runs had become very slow. The reason turned out to be the window size: in the virtual display a 1080p window only reaches about 15 frames per second, while a 960x540 window runs at a steady 60. Since the game's clock follows its frames, the small window makes everything about four times faster. The old input scripts also pressed keys at fixed times, which went wrong whenever loading took longer than usual.

The new runner, `scripts/autotest.sh`, keeps the window small, keeps pressing Start until the game's own log says the main menu is ready, then plays the rest of the key presses timed from that moment and stops as soon as the scene it wants has been captured. A full trip into a match now takes about two and a half minutes, unattended, and each run writes a short summary with the time to the menu, the average frame rate and the most frequent warnings. `scripts/sweep.sh` queues runs with different engine settings, so a whole set of experiments can run in one go. The launcher also accepts engine options after `--` that replace its own defaults, which the runner uses for the window size.

One visual bug is clear now. In the National TT Auditorium the floor shows up red and lit during the venue fly-over, but during play the floor around the table is completely black, with no shadows. The menu's arena floor draws correctly. Turning off background shader compilation and switching to the other render-target method both leave the floor black, so it is not caused by either of those. A sweep over the depth, resolve and gamma options did not change it either.

Later in the night I narrowed it down further with a locally patched copy of the graphics SDK that can log every draw of one frame, skip or recolour draws by shader, and report what the resolved render targets contain. Drawing candidate shaders in solid magenta showed that the floor is drawn, as a single quad by one pixel shader, and that this shader produces black. The shadow maps it depends on are correct, and the floor's vertex colours and textures are fine. Its light comes from a half-resolution light mask that an earlier pass builds from the spotlight's cookie texture. Forcing the cookie, the light mask or the floor textures to white still leaves the floor black, so the cause sits between those inputs and the shader's output. The next step is a proper frame capture to look at that pass directly.

Two smaller findings from the same work: every test run that ended by being killed left a 4.5 GB guest-memory file behind in shared memory, which eventually filled it and crashed later runs; the test runner now removes those files. And the repeating "call to NULL" warning comes from a media-stream decoder object that was never created, not from rendering.

## 2026-10-31 — The black floor, found and fixed

The dark arena turned out to be a bug in the graphics SDK, not in the game code. With RenderDoc installed I could capture match frames and step through the floor's pixel shader on a real pixel. The vertex colour and the lighting inputs arrived intact, but every texture sample came back scaled down by 2 to the power of -13. That factor comes from the texture's exponent-adjust field, and the Vulkan shader translator was reading it from the wrong word of the texture descriptor: word 4, where the LOD bias lives, instead of word 3. Any texture with a LOD bias, which includes the arena floor and the players' skin, was effectively multiplied down to black. The Direct3D 12 path on Windows reads the right word, which is why the Windows build never showed it.

The fix is a few lines, kept as a patch in `project/sdk-patches/` that `build.sh` applies to the pinned SDK source before building it. A second small patch stops the SDK from loading RenderDoc into every run whenever it is installed. The floor is now red and lit with the table's shadow on it, the players' faces and arms are lit, and the character select screen shows the player properly instead of a dark silhouette. Two runs agree.

Getting there needed better tools than screenshots: a way to launch the game under RenderDoc from the test runner and capture a burst of frames in a match, and a few headless RenderDoc scripts that find a draw by its shader, read the vertex shader outputs, and dump a full shader debug trace for a pixel.

## 2026-10-31 — Soak test, Steam Deck package and the PC options

A 20-minute unattended session of back-to-back Exhibition games ran without a crash, with correct lighting throughout. Matches ran at about 47 frames per second in the virtual display, which looked like a problem until a smaller window brought them to a flat 60: the cost is copying frames into the virtual display, not the game. Profiling still turned up three threads that spin instead of sleeping (the audio worker, the frame pacer and a game thread waiting on the GPU), which costs nothing on a desktop but matters on the Steam Deck's smaller CPU.

The Linux build needed glibc 2.44, newer than SteamOS ships, so there is now a portable build made in an Ubuntu 24.04 container with clang 20 and the C++ runtime bundled alongside the game. It needs glibc 2.38, contains nothing from the disc, and a small setup script extracts and patches the menu files from your own ISO on the Deck and picks the new 1280x800 preset. It plays a full match on this PC; the Deck itself is next.

The PC options from the Windows version all work on Linux: 120 FPS and uncapped play at well over 100 frames per second, the 1440p and 4K internal resolutions and both FXAA modes hold 60 with no errors. The exception is AMD FidelityFX (FSR and CAS sharpening): its build runs AMD's Windows shader compiler under Wine, which rejects macro definitions with the current glslang, so Linux keeps bilinear filtering for now.

## 2026-11-01 — Running on the Steam Deck

The game now runs on a Steam Deck (SteamOS 3.8) at a steady 60 frames per second, with the Deck's own controls working as a real gamepad. Launched outside Steam, the Deck's desktop controller layout turns B into Escape, which quit the game on the spot, so on Linux Escape now has to be pressed twice within two seconds. Started as a non-Steam game, Steam presents the controls as an Xbox-style pad and everything works.

The first sessions had occasional hitches. Lining up the frame-rate log with the shader log showed why: every dip came right after a burst of new graphics pipelines being compiled, about nineteen in two seconds against almost none otherwise. The game keeps those pipelines in its cache and builds them at startup next time, and the third session started with 153 of them ready and ran without dips.

Profiling here also turned up the SDK's audio worker spinning a whole CPU core. Waits on Linux are cut into one-millisecond slices, and the remaining time was rounded down to whole milliseconds, so the last fraction became a zero-length sleep and the thread spun instead of sleeping. Sleeping for the real remaining time brought it from 99% of a core to about 5%, which on the Deck's four cores leaves room for the game. On the Deck the processor now sits about 70% idle during a match and the graphics chip at about 40%.

## 2026-11-01 — Full speed and the right shape on the Steam Deck

On the Deck the game looked smooth but played in slow motion: the screen updated sixty times a second while the game itself produced only 24 to 27 frames, and since it advances its simulation once per frame, matches ran at about 40% speed. The music plays on its own clock, which is why it sounded fine. A new log line now reports the game's own frame rate next to the presentation rate, which made the gap visible.

Sampling every thread's call stack during a match showed where the time went. The emulator watches the parts of memory the GPU reads, so a game write there traps into a handler, and that handler asked for the page's protection by reading and parsing /proc/self/maps as text, line by line, every time, while holding a lock the GPU thread needed as well. The kernel can answer that question directly with one call (PROCMAP_QUERY, Linux 6.11 and later; the Deck runs 6.16), and with that the Deck plays matches at 47 to 60 game frames per second and feels like normal speed. Older kernels keep the old method as a fallback.

The picture was also the wrong shape. The SDK told the game its TV had the same proportions as the window, so the Deck's 16:10 screen stretched the 16:9 image, and smaller windows even made the game switch to its 4:3 standard-definition layout. The game now always sees its native 1280x720 mode, and the image is letterboxed rather than having its edges cropped as TV overscan, so the Deck shows the full picture undistorted with thin bars above and below. Filling the whole screen, as ultrawide mods do, would mean changing the game's own camera and render size and is a possible next project.

## 2026-11-01 — From a working port to something people can install

The Steam Deck runs the game at a steady 59 to 60 frames per second now, and sleeping and waking the Deck in the middle of a match works without a hitch. The last attempts at more speed taught their own lessons: building for newer CPUs and skipping a debug lookup on every GPU register write changed nothing measurable, uncapped frame rates make things worse because the game advances once per frame and the extra presenting competes with the emulated GPU, and rendering at twice the resolution pins the Deck's GPU at 99 percent and drops the game to slow motion. The Deck keeps the plain 720p render; a `render_scale` option stays for PCs with GPU headroom.

Most of the day went into making the port feel like it belongs to the game. Achievements already came from the disc; now an unlock slides into the corner of the picture in the game's own menu style, with a short sound made in code: a whoosh, two ping-pong bounces and a marimba roll, picked from three candidates after the first two-note chime turned out to be grating. Holding the View button opens the list. The game's OPTIONS menu, in the main menu and in the pause menu, got a real PC SETTINGS entry: the menu is a Flash movie, and the entry is added by rewriting two small pieces of its bytecode in place on your own copy, while a hook on the game's own flag check opens a settings page drawn like the game's option screens. Moving the entry up one row showed that the movie fills in its translated labels by row number, so that script needed adjusting too.

The game only rumbles on a few shots, so there is now a pulse on every hit, taken from the moment the game updates its rally counter, and a tick when moving through menus. On the Deck only the low-frequency motor is felt, which is why the first version was barely noticeable.

The biggest piece is the installer. Because the game is compiled from the code on your disc, it cannot be shared ready-made, so like the Windows version the installer builds it on your machine. A game-styled window takes your ISO (dropped, browsed, or found on an SD card), checks it, lets you choose where to install and whether to add it to Steam for Game Mode, and ends with a PLAY button. Everything that does not come from the disc is prebuilt and published: a slim set of build tools and the engine, about 125 MB together. With those, a first install took 49 seconds on this PC, downloading from GitHub included; switching to LLVM's own clang build made the game compile half again as fast as Ubuntu's. Without them the installer still gets whatever is missing by itself, down to unpacking an official Ubuntu base system without admin rights.

Updates go through the same machinery. The launcher checks for a new release in the background, the main menu shows a popup, and PC SETTINGS offers the update with its notes; the game closes, the installer's window rebuilds it in seconds and the game starts again, with saves and settings kept. Releases are signed, and a tampered release is refused. Testing the update path end to end found two real bugs before anyone else could: a signature helper that silently replaced a file-comparison function with the same name, and the update window reading an empty list of install locations and crashing at start.

Linux 1.0.0 is published as the first release.

## 2026-11-01 — System link: two machines, one match

The retail game still contains Rockstar's network code for system link, the Xbox 360's LAN play. The session layer has a debug switch (the `-forcesyslink` parameter) that makes the normal Xbox LIVE menus create and find sessions by LAN broadcast instead of Live matchmaking, so the whole online front end (player match, lobby, match, results) works over the local network once that switch is set. The main menu's online entry, removed by the offline patch, is back as SYSTEM LINK, and the offline blocks in the executable now only apply when system link is turned off.

The engine's network layer needed the most work. It returned a loopback address as the console's own address, could not turn a peer's console address into an IP address, had no QoS and no `getsockname`, passed Windows socket option numbers straight to Linux, reported no socket errors, and handed out socket handles above 0x80000000, which the game's code treats as invalid, so its socket was closed as soon as it was opened. Each machine now reports its LAN address, ports are shifted by 10000 because Linux reserves those below 1024 for root, broadcasts go out with the right socket option, and the session identity is created when a match is hosted.

The rest came from watching the game's own debug messages, which the retail build still formats but sends nowhere; routing them to the log (`TT_GAME_LOG=1`) explained each stall. The host turned every join away because both machines were signed in as "User" and the session keeps players by name, so the profile name is now the computer's host name. The game keeps one connection per peer address but talks to the same peer in two sessions at once, a game session and a spectator session; on the console every session gets its own private address for a peer, so the port now does the same and tags those packets with the session. Finally the lobby waited for a "registered for arbitration" notice before starting, which only Xbox LIVE's ranked service sends; for system link a successful session start now counts as that.

Two instances on one machine, each on its own loopback address, now find each other, join the same lobby and play a match with the score in sync on both screens (`scripts/lan-test.sh`). A test on two real machines on the same network is next.

## 2026-11-02 — Online play through a small server

System Link over Tailscale worked, but it asked players to set up a VPN, addresses and ports. Online play now goes through a small server instead (`server/ttlink_server.py`, Python standard library only). The server is a virtual LAN: players connected to the same room see each other as one network. The game's own System Link broadcasts, its match search and announcements, are passed to the other players in the room, so QUICK MATCH and CREATE MATCH work exactly as on a LAN. Once two players are in a room the server introduces them and they open a direct path through their routers (UDP hole punching); when that fails, the server relays their packets. Relaying only happens between members of the same room, every client has a packet and byte budget, and nothing is stored.

On the game side the main menu now has ONLINE in the old Xbox LIVE row and SYSTEM LINK below it, and both lead into the game's own online menus. ONLINE first shows a small prompt in the style of the PC SETTINGS page: PLAY ANYONE for the public room, or PLAY WITH A FRIEND, which either shows a six-character room code to share or lets you type your friend's code with the D-pad. Telling the two menu entries apart took some digging: the game only asks for its online menu from row 3 of the main menu, so the menu patch now asks for it from both rows and leaves the chosen row where the executable can read it.

The engine's network layer got an online client: while online, every datagram the game sends goes to a room member directly or through the server, and the machine's address is the one the server assigned in the room. One last problem was that the game reads its own network address once, at sign-in, and keeps it in its peer description; the host then saw the guest under its old LAN address and the join timed out. The game refreshes that description itself after a sign-in change, so the port now asks it to do the same when the online address changes.

Two instances on one machine with a local server now meet in a private room and play a match over a direct connection, and in the public room with every packet relayed through the server. A player in another room does not see the match, and System Link on the LAN still works. The server needs a small virtual machine with a public address before anyone can use it; until then ONLINE says that online play is not available yet.

## 2026-11-02 — How good is the connection, and who is close

The first real online match, a Steam Deck in India against this PC over a phone hotspot, worked but felt slow: every hit waited for a round trip of 340 to 400 milliseconds, and lost packets made it worse. Players should see that before they start, so the online client now pings the other player once a second over the same path the match uses, direct or through the server, and keeps a smoothed round trip and the share of lost pings. Outside matches a small box in the corner shows it as bars, milliseconds, loss and the path, green, yellow or red, with a warning when the match will feel delayed (over 150 ms or 2% loss). The log gets the same numbers every ten seconds.

The server now helps people find players close to them. Each client reports its round trip to the server and its time zone, nothing more precise. The estimated distance between two players is the smaller of the sum of their round trips to the server and a guess from the time zone difference, which covers two neighbours far from the server. In the public room a match search first only reaches players within about 100 ms; if nobody answers, searching again looks further, and after about forty seconds of searching everyone is in reach. Private rooms stay unfiltered, since friends always want to see each other. The ONLINE prompt shows how many players are near you.

To test this without a second continent the client can delay or drop its own packets on request. With one instance delayed by 300 ms and reporting India's time zone, its first quick match found nothing, the second found the host on this PC, the box showed 300 ms with the warning on both sides, and the match played.

## 2026-11-02 — On a Mac, and settings that apply at once

The game now builds and starts on a MacBook with an Apple M2. The engine already knew how to draw through MoltenVK, which turns Vulkan into Metal, so most of the work was in the build: the scripts assumed GNU tools and a newer bash than macOS ships, one of upstream's tools needed Python 3.10 where the Mac has 3.9, and the runtime libraries and MoltenVK had to be copied next to the game.

The first start showed a black window. A sample of the threads found the game's main thread stuck in a signal handler: one floating-point add kept faulting, and the engine's fault handler returned without handling it, so the same instruction ran again forever. Two fixes came out of it. The fault handler now reports a fault nobody claims and lets the process crash with a proper report instead of spinning, on every system. And the crash report itself named the real problem: a trapped floating-point exception, inexact result. The project's FPSCR override kept exceptions "disabled" by setting the mask bits, which is right on x86, where a set bit masks the exception. On ARM the same bits enable the trap, and Apple's chips honour them. Each platform now has its own way of keeping traps off, and the x86 code is unchanged.

The game runs on the Mac now, but slowly: around 25 to 34 game frames per second and fewer on screen. Samples show both threads that feed the GPU waiting for it, about 100 ms per frame, so the GPU itself is the bottleneck. A GPU trace with Xcode's Metal tools is the next step. The other render path, which avoids switching render targets on tile-based GPUs, drew the picture wrongly through MoltenVK, so it is not an option. VSync is on by default on the Mac now, which removes the tearing.

PC SETTINGS grew a player name and a manual update check. The name editor works like the room code entry, with the D-pad or a keyboard; because every copy of the game has the same Xbox ID and players are told apart by name, the online server now refuses a second player with a name that is already in the room. CHECK NOW runs the same signed update check as the launcher, as a separate process so the page keeps working, and offers the new version straight away.

Most settings now apply at once instead of after a restart. Anti-aliasing and sharpening switch through two small runtime calls, VSync rebuilds the swapchain after the frame, and 720p, 800p and 1080p resize the window. The picture setting went furthest: davidptrssvea's widescreen work from the Windows version, a wider camera with menus kept 16:9 and clipped to that area, came over as four native edits whose hashes matched this port's generated code unchanged. It now follows the window as it is resized, so a wide window gets a wider view straight away, and FILL on the Steam Deck's 16:10 screen shows more at the top and bottom. Only the player name and the two highest resolutions still wait for a restart.

Keyboard controls are there for testing without a controller, off by default, with keys that follow the controller layout from the game's own controls screen.

## 2026-11-03 — Tabs, a cooler GPU wait, and PlayStation buttons

PC SETTINGS had grown to seventeen rows, so it is split into four tabs now, DISPLAY, GAME, ONLINE and UPDATES, switched with the shoulder buttons. Each tab has room for its descriptions again.

The game waits for the GPU in a tight loop. On the Xbox that loop paused the hardware thread between polls; recompiled, it spun a CPU core at full speed. A small native edit now sleeps 100 microseconds before each poll. In a match on the desktop that took CPU use from about 1.8 to 1.7 cores with frame times unchanged at 16.67 ms; on the Steam Deck it made no measurable difference to battery life (see below).

The button icons were the interesting one. The menus draw A, B, X, Y, LB and RB as small textures inside each Flash movie, nine movies with their own copies, all DXT5 in the Xbox's tiled layout. Rather than ship a second set of menus, the engine got a hook that lets the game look at a texture just before it goes to the GPU. The game recognises each Xbox icon by a fingerprint of its compressed blocks and writes its own PlayStation artwork in its place, compressed and tiled the same way; the Xbox data it saw is kept, so switching back restores it. Getting a switch to show in a menu that is already open took one more step: writes from outside the guest skip the engine's memory watch, so the game now reports them the way the kernel does after reading a file, through all three views of physical memory, and the GPU loads the icons again. The source keeps only the fingerprints, never the game's images. BUTTON PROMPTS on the GAME tab picks AUTO, which follows the type of the controller used last, XBOX or PLAYSTATION, and the settings page and achievements list draw their own icons to match.

## 2026-11-03 — Watching a match: first steps

The game has spectating built in: CREATE MATCH has ALLOW SPECTATORS, the CUSTOM MATCH list shows matches in progress, and the HUD counts spectators. A third copy of the game now joins the System Link tests (scripts/lan-test.sh, TT_SPEC_SCENARIO). In the first three-way test the host and guest played a whole match and the third machine saw it in its list, but selecting it did nothing. The list measures the connection to each match before it lets you in, and every measurement went to address 0.0.0.0: the list keeps a session's ID but not its host's address. The host now puts its address into the session ID it creates, and the measurement reads it from there (online, the client reports its own round trip to that player instead). The list shows a proper connection now, and selecting the match connects to the host, which answers. The game then says it failed to connect to the session: when a match starts the host moves into a second session for the match, while the list still offers the lobby's. That handshake is the next thing to understand.

Spectating works now. The way in is TABLE TENNIS NETWORK > EXHIBITION, which searches for matches to watch. That search found the match but connected to the lobby, which has room only for the two players: on Xbox LIVE a spectator's search went through matchmaking, which only lists the match session the host creates when play starts, while over System Link the host answers every search with its lobby. While the lobby is closed to joins in progress, the host's search answer now names the match session instead (the same session info, swapped in the network layer). The third machine then joins the match session, sees the lobby with SPECTATE MATCH, and watches the match live with the score and the spectator camera, while the two players carry on undisturbed.

The same three-way test through a local copy of the online server works too, and a full match settled the online achievements. The host set one game to 7 points, the guest held its aim wide to lose, and the third machine watched from start to finish. At 7-1 the host got THE VICTOR and THE NOOB, the guest THE NOOB, and the spectator THE SPECTATOR, each with its popup. The test script gained a `hold` command for that (scripts/scenarios/online-*.txt).

Automatic reconnect came down to one number. A test that dropped everything one player sent for 6 seconds, once every minute and a half, ended the match at the first drop with no result. The game's network tuning (tune/net/PongNet.NetTuningData) sends an unacknowledged message again every 150 ms in a match and gives up after 20 tries: three seconds of silence and the connection counts as lost. In memory each policy starts with the retransmission time, the connect timeout and then the retry count, which a dump of the live tuning showed after a first attempt looked for them in the order of the text file. With 100 retries in a match (and 50 instead of 10 for spectators, at 300 ms) the game waits about 15 seconds; the same test played through two drops to a normal 7-1 finish, achievements included.

Measured on the Steam Deck, the GPU-wait change turned out not to matter for battery life. The battery reports its current and voltage, so a test build started from Steam sat in the main menu (the demo match plays behind it) and the power draw was read once a second for 90 seconds, with the change off and on: 10.62 W and 10.56 W, the difference within the noise, against 5.6 W for the Deck at rest. The desktop's CPU saving does not show up in the Deck's power draw, which the GPU, screen and the rest of the system dominate. The change stays, since it costs nothing; at about 10.5 W the game runs roughly three and a half to four hours on a charge.

## 2026-11-03 — Release 1.3.0

Version 1.3.0 is out with everything above, and the online server is reached by name now (rockstartt.duckdns.org, with its address as a fallback), so it can move without another update. The server itself got key-only SSH, fail2ban and automatic security updates.
